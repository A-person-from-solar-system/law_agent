# 法律 Agent 评估指标

## 1 评估目的

当前系统从业务能力、通用 Agent 能力和工程能力三个层面进行评估。业务能力回答“法律回答是否可靠”，Agent 能力回答“模型是否正确使用上下文和工具”，工程能力回答“整个服务链路是否稳定、可观测并且成本可控”。

评估结果应同时保留最终回答、工具调用参数、工具返回摘要、SSE 事件、运行日志、token 用量和错误码。不能只根据最终回答是否流畅进行判断。

## 2 通用评估规则

1. 业务评测使用脱敏案件，由业务人员标注事实、争议点、法律依据、必须覆盖内容和禁止错误。
2. Agent 行为评测优先使用固定测试集和 Mock RAG，避免知识库结果变化影响对比。
3. 工程评测在固定模型、Prompt、RAG 配置和并发条件下运行。
4. 每次评测记录代码版本、模型版本、Prompt 版本、数据集版本和运行时间。
5. 关键样例建议重复运行 3 次，分别统计平均结果和最差结果。
6. 优先使用程序可以确定的评分规则，语义判断再由业务人员或经过人工校准的大模型评分器完成。

以下情况直接记为严重失败，不能用其他指标的高分抵消：

- 编造法条、案例、案号或 `sourceId`；
- 将其他案件的人员、金额、时间或证据用于当前案件；
- 调用未授权工具或越权访问数据；
- RAG 失败或无结果时声称检索成功；
- 给出明显违反已提供案件事实的确定性结论。

## 3 业务能力指标

业务能力主要由业务人员评审，建议每个维度按 0 至 4 分评分：0 分表示完全错误，1 分表示存在严重问题，2 分表示部分正确，3 分表示基本正确，4 分表示完整且可靠。

| 指标 | 评估内容 | 评估方式 |
| --- | --- | --- |
| 事实识别准确性 | 是否准确提取人物、金额、时间、行为、责任和案件结果 | 与人工标注的事实要点对比，统计事实准确率和遗漏率 |
| 事实状态区分 | 是否区分已确认事实、用户主张、对方主张和模型推断 | 人工检查是否把未经确认的陈述写成确定事实 |
| 法律依据准确性 | 引用的法条、司法解释和案例是否与问题相关且仍可适用 | 业务人员核验法律依据及其适用条件 |
| 来源可追溯性 | 回答中的法律依据是否带有本轮检索返回的有效 `sourceId` | 自动比对回答引用与本轮 RAG 返回结果 |
| 争议焦点覆盖度 | 是否识别案件的主要争议，而不是只复述案情 | 与人工标注的争议焦点清单对比 |
| 法律分析合理性 | 事实、法律依据和结论之间是否形成合理分析链路 | 业务人员按照参考分析要点评分 |
| 责任或量刑分析 | 是否考虑责任比例、后果、主观状态和从宽从重情节 | 针对相应案由进行专项人工评分 |
| 信息不足处理 | 事实不足时是否主动说明限制并提出必要追问 | 检查是否在信息不足时直接给出确定结论 |
| 风险提示 | 是否说明类案差异、证据限制和正式法律意见边界 | 人工检查必要提示是否完整且不过度重复 |
| 可操作性 | 是否给出明确的补充材料、核验方向或后续处理建议 | 人工判断建议是否与当前问题相关并可执行 |

建议汇总指标：

- 业务平均得分；
- 事实准确率；
- 争议焦点召回率；
- 法律依据有效率；
- 有效来源引用率；
- 严重法律错误率；
- 业务人员判定的整体合格率。

## 4 通用 Agent 能力指标

### 4.1 工具调用判断

使用 `test_data/tool_test.json`，将人工标注的“应调用或不应调用”与实际是否出现 `search_legal_kb` 的 `tool.started` 事件进行对比。

| 指标 | 计算或判断方式 |
| --- | --- |
| 工具调用准确率 | 正确调用和正确不调用的样例数 ÷ 总样例数 |
| 工具调用精确率 | 正确调用数 ÷ Agent 实际调用工具的样例数 |
| 工具调用召回率 | 正确调用数 ÷ 人工标注应调用工具的样例数 |
| RAG 误调率 | 不应调用但实际调用的样例数 ÷ 不应调用样例数 |
| RAG 漏调率 | 应调用但没有调用的样例数 ÷ 应调用样例数 |
| 追问正确率 | 信息不足的样例中，先追问而不是盲目检索的比例 |

### 4.2 查询参数生成

使用 `test_data/query_parameter.json`。不要求 Agent 生成与参考答案完全一致的查询语句，而是检查查询参数是否保留人工标注的核心语义。

| 指标 | 计算或判断方式 |
| --- | --- |
| 必需要素召回率 | 实际 query 覆盖的必需要素数 ÷ 人工标注的必需要素数 |
| 错误要素引入率 | query 中不存在于问题和上下文的错误条件数 ÷ 全部提取条件数 |
| 案由识别准确率 | 是否提取了正确案由或法律关系 |
| 附加条件保留率 | 时间、地区、责任比例、金额和从宽情节等重要条件的保留比例 |
| `sourceTypes` 合理率 | 法条、案例和知识类来源类型是否与任务匹配 |
| 改写稳定性 | 同一基础问题的不同表达是否形成语义一致的查询 |
| 查询整体合格率 | 人工判断查询是否足以支持有效检索的比例 |

### 4.3 工具结果使用

使用 `test_data/tool_reslut.json`，通过 Mock RAG 返回固定的相关证据、无关证据、重复证据和冲突证据。

| 指标 | 计算或判断方式 |
| --- | --- |
| 来源引用有效率 | 回答中属于本轮 RAG 返回结果的 `sourceId` 数 ÷ 回答引用的全部 `sourceId` 数 |
| 核心证据使用率 | 实际使用的必选证据数 ÷ 人工标注的必选证据数 |
| 无关证据误用率 | 被禁止证据实际用于结论的样例数 ÷ 含干扰证据的样例数 |
| 虚假来源率 | 出现本轮结果中不存在的 `sourceId` 的样例比例 |
| 重复证据处理正确率 | 是否没有把重复召回当成多个独立来源 |
| 证据与结论一致率 | 人工判断结论是否真正得到引用证据支持 |
| 证据限制识别率 | 对过期、截断、知识摘要或冲突证据是否给出正确限制说明 |

### 4.4 多轮与多案件切换

使用 `test_data/case_change.json`，逐轮检查 `activeCaseId`、案件事实和来源范围。

| 指标 | 计算或判断方式 |
| --- | --- |
| 当前案件识别准确率 | 回答使用正确 `activeCaseId` 对应案件的轮次数 ÷ 总轮数 |
| 当前案件事实召回率 | 回答覆盖的当前案件必需事实数 ÷ 标注事实数 |
| 跨案件事实污染率 | 使用其他案件人员、金额、日期或责任信息的轮次比例 |
| 来源范围正确率 | 回答引用的来源是否属于当前轮或明确允许的历史材料 |
| 省略指代处理正确率 | “这个案件”“刚才那个”等表达是否根据当前绑定案件正确解析 |
| 通用问题隔离率 | 没有绑定案件时，是否避免把上一案件事实带入通用回答 |
| 明确跨案比较正确率 | 用户明确要求比较时，是否分别说明案件事实而不进行错误合并 |

### 4.5 工具失败处理

使用 `test_data/tool_failure.json`，模拟无结果、超时、连接失败、无效响应、调用上限和部分结果等情况。

| 指标 | 计算或判断方式 |
| --- | --- |
| 失败状态说明率 | 是否明确说明检索没有正常完成 |
| 错误类型识别率 | 系统记录的错误码是否与模拟故障一致 |
| 安全降级率 | 能否在明确限制的前提下给出有限说明或合理重试建议 |
| 失败后编造率 | 工具失败后仍编造法条、案例或 `sourceId` 的样例比例 |
| 无限重试发生率 | 是否超过工具调用上限或反复调用同一失败工具 |
| 部分结果说明率 | 结果被裁剪或只返回部分材料时，是否避免声称覆盖全部结果 |
| 运行结束正确率 | 应继续回答时是否合理继续，应中止时是否通过 `run.failed` 正确结束 |

### 4.6 上下文与指令能力

| 指标 | 评估内容 |
| --- | --- |
| 指令遵循率 | 是否执行用户有效要求，同时不接受改变系统规则的指令 |
| 长上下文稳定性 | 增加历史消息和案件材料后，核心事实和任务目标是否保持一致 |
| checkpoint 一致性 | 压缩前后对关键事实、未解决问题和案件归属的理解是否一致 |
| 当前问题关注度 | 是否围绕用户本轮问题回答，避免被中间位置的无关材料干扰 |
| 自我纠错能力 | 用户指出错误后，是否核验并修正，而不是坚持错误结论 |

建议将不同能力分别报告，不只输出一个总分。工具选择、案件隔离和来源真实性属于关键能力，需要单独设置发布门槛。

## 5 工程能力指标

工程指标主要从 `AgentRun`、`AgentToolCall`、`AgentRunEvent`、SSE 事件和服务日志中统计。

### 5.1 可用性与成功率

| 指标 | 计算或判断方式 |
| --- | --- |
| Agent Run 成功率 | `run.completed` 数 ÷ Agent Run 总数 |
| Agent Run 失败率 | `run.failed` 数 ÷ Agent Run 总数 |
| SSE 正常完成率 | 建立 SSE 后最终收到 `run.completed` 或可识别 `run.failed` 的比例 |
| 工具调用成功率 | 成功的 `tool.completed` 数 ÷ 工具调用总数 |
| RAG 可用率 | 正常返回可解析响应的 RAG 请求数 ÷ RAG 请求总数 |
| 错误提示覆盖率 | 后端错误是否都转换为前端可识别错误码和安全提示 |

### 5.2 性能指标

| 指标 | 计算方式 |
| --- | --- |
| 首字延迟 TTFT | `run.started` 到第一个 `text.delta` 的时间 |
| 总响应时间 | `run.started` 到 `run.completed` 或 `run.failed` 的时间 |
| RAG 调用耗时 | `tool.started` 到对应 `tool.completed` 的时间 |
| 模型生成耗时 | 模型开始生成到最后文本或完成事件的时间 |
| P50 P95 P99 延迟 | 分别统计上述耗时的中位数及高分位值 |
| 超时率 | Agent、模型或 RAG 超时请求数 ÷ 总请求数 |

### 5.3 成本与上下文指标

| 指标 | 计算或判断方式 |
| --- | --- |
| 平均输入 token | 所有成功请求输入 token 总数 ÷ 成功请求数 |
| 平均输出 token | 所有成功请求输出 token 总数 ÷ 成功请求数 |
| 单轮平均总 token | 每轮输入和输出 token 之和的平均值 |
| 上下文预算超限率 | `CONTEXT_BUDGET_EXCEEDED` 数 ÷ 请求总数 |
| checkpoint 触发率 | 生成 checkpoint 的会话数 ÷ 达到触发条件的会话数 |
| 压缩率 | 压缩前估算 token 与摘要 token 的减少比例 |
| 压缩信息保留率 | checkpoint 是否保留人工标注的关键事实、结论和待解决问题 |

### 5.4 并发与隔离指标

| 指标 | 计算或判断方式 |
| --- | --- |
| 并发成功率 | 指定并发量下成功完成的请求数 ÷ 总请求数 |
| 吞吐量 | 单位时间完成的 Agent Run 数量 |
| 并发延迟变化 | 并发增加前后 P95 首字延迟和总耗时的变化 |
| 用户串话率 | 回答出现其他用户数据的请求数 ÷ 并发请求数 |
| 案件串话率 | 回答出现其他案件事实的请求数 ÷ 并发请求数 |
| 连接池与资源错误率 | 数据库连接、HTTP 连接池、内存或文件句柄相关错误比例 |

### 5.5 可观测性与故障定位

| 指标 | 评估内容 |
| --- | --- |
| Trace 完整率 | 每次请求是否能通过 `requestId` 关联 Run、工具调用、SSE 事件和错误 |
| 工具日志完整率 | 是否记录工具名、参数摘要、耗时、状态、错误码和 `sourceId` |
| 错误分类准确率 | RAG、模型、上下文和 Agent 连接异常是否进入正确错误类别 |
| 敏感信息泄露率 | 日志和浏览器事件中是否出现密码、token、完整敏感案情或内部密钥 |
| 故障定位成功率 | 能否仅根据日志判断问题位于中台、Agent、模型还是 RAG |

## 6 建议发布门槛

以下数值是首版建议，应在获得基线数据和业务意见后调整，不能描述为当前系统已经达到的结果。

| 指标 | 首版建议门槛 |
| --- | ---: |
| 法条、案例或 `sourceId` 编造率 | 0 |
| 跨案件事实污染率 | 0 |
| 越权工具调用次数 | 0 |
| 工具调用召回率 | 不低于 95% |
| 工具调用精确率 | 不低于 90% |
| 查询必需要素召回率 | 不低于 90% |
| 来源引用有效率 | 100% |
| 工具失败后编造率 | 0 |
| 评测环境 Agent Run 成功率 | 不低于 99% |
| SSE 正常完成率 | 不低于 99% |
| Trace 完整率 | 100% |

性能指标不建议直接写死统一数值。应先在固定模型和硬件上建立基线，再结合用户体验确定首字延迟和总耗时目标。新版本的 P95 延迟、token 消耗或失败率如果比基线恶化超过约 15%，应进行原因分析后再决定是否发布。

## 7 评估报告内容

每次完整评估至少输出以下内容：

1. 代码、模型、Prompt、RAG 和数据集版本；
2. 三个能力层面的指标结果；
3. 与上一版本的变化；
4. 严重失败和高频失败案例；
5. 失败原因分类；
6. 延迟、token 和错误码分布；
7. 人工复核结论；
8. 是否满足发布门槛；
9. 后续修复项及负责人。

评估分数用于发现问题，运行轨迹用于解释原因。Agent 低分时，应先检查任务是否存在歧义、Mock 环境是否正确以及评分器是否过于僵化，再判断是否确实是模型、Prompt、RAG 或上下文管理能力不足。
