# 法律 Agent 初期评估方案

## 1 评估数据集

评估初期先准备 20 至 50 个 Task，跑通数据构建、Agent 执行、自动评分和人工复核流程。

当前系统主要构建两类评测集：

1. **端到端业务评测集**：判断最终回答是否满足业务要求；
2. **工具调用判断评测集**：判断 Agent 是否在正确的场景调用 RAG。

## 2 端到端业务评测集

### 2.1 数据来源

从业务人员提供的、没有存入当前知识库的脱敏案件中，按照案件类型抽取一部分样本。每个样本包含：

- 原始案件信息；
- 专家处置意见；
- 人工标注的事实要点；
- 应参考的法律依据；
- 处置建议要点。

### 2.2 Task 结构

每条 Task 由问题、参考行为和评价标准组成。

| 组成 | 内容 |
| --- | --- |
| 问题 | 请分析案件事实、适用依据并给出处置建议 |
| 参考行为 | 事实要点、核心法律依据和处置建议要点 |
| 评价标准 | 事实识别、来源追踪、法律依据和处置建议等 Rubric |

一条 Task 可以同时使用多个指标进行评价，不需要为每个指标单独构建一套案件数据。

## 3 业务指标 Rubric

### 3.1 事实识别准确性

- **输出方式：** Agent 在正常分析正文末尾输出固定 `FACTS_JSON`，包含人物、时间、地点、行为、关键数值、责任和案件后果七类字段。
- **Rubric：** 一个输出事实与人工事实在字段和值上匹配才记为正确；人工事实未输出记为遗漏；无法匹配人工事实的输出记为错误输出。
- **精确率：** Agent 正确提取的事实数 ÷ Agent 提取的全部事实数。
- **召回率：** Agent 正确提取的事实数 ÷ 人工标注的必要事实数。
- **单 Task 得分：** 使用精确率和召回率计算 F1。
- **判定方式：** 程序解析 `FACTS_JSON`，对字段和值进行归一化、数字匹配和常用同义表达匹配，再逐项计算 TP、FP、FN；当前不再由 LLM Judge 直接给出计数。
- **格式错误：** 未返回合法 `FACTS_JSON` 时，该 Task 的事实识别得分记为 0，并标记 `invalid_structured_output`。
- **严重错误：** 编造案件材料中不存在的人物、金额、时间或案件结果。

### 3.2 来源可追溯性

- **评估目标：** 判断 Agent 回答中引用的法律依据是否来自本轮 RAG 返回的结构化结果，避免模型编造不存在的来源。
- **Rubric：** 回答中引用的每个 `sourceId`，是否都能在本轮 RAG 返回的 `sourceId` 集合中找到。
- **单 Task 得分：** Agent 回答中有效的 `sourceId` 数量 ÷ Agent 回答引用的 `sourceId` 总数。
- **总分：** 所有参与计算的 Task 得分的平均值。
- **判定方式：** 从 Agent 回答中提取全部 `sourceId`，与本轮 RAG 工具返回结果进行自动比对。
- **特殊情况：** Agent 调用了 RAG 并给出了法律依据，但没有引用任何 `sourceId`，该 Task 记为 0 分；不需要调用 RAG 的 Task 不参与该指标计算。
- **严重错误：** 引用本轮 RAG 未返回或根本不存在的 `sourceId`。

### 3.3 法律依据准确性

> **当前状态：暂不实现。** 当前系统的 RAG 尚未包含可用于核验法条时效性和适用性的法律数据，因此本阶段保留该指标的设计，但不执行评分，也不计入评测总分或发布门槛；待法律知识库接入后再启用。

- **Rubric：** 法律依据是否相关、现行有效、覆盖核心法条，并且没有无关或错误引用。
- **精确率：** 正确且可适用的依据数 ÷ Agent 引用的全部依据数。
- **召回率：** Agent 命中的核心依据数 ÷ 人工标注的核心依据数。
- **单 Task 得分：** 使用精确率和召回率计算 F1；触发一票否决项时，该 Task 直接记为 FAIL。
- **判定方式：** 先匹配法条编号和名称，再由 LLM Judge 判断相关性和适用性，最后由业务人员抽检。
- **一票否决：** 编造法条、引用明确失效的规定，或者将明显无关的法条作为核心结论依据。

每条 Task 的人工法律依据可以分为：

- `required`：必须覆盖的核心依据；
- `acceptable`：允许引用的补充依据；
- `forbidden`：错误、失效或明显不适用的依据。

### 3.4 处置建议合理性

- **Rubric：** 是否考虑责任比例、行为后果、主观状态、从宽情节、从重情节，以及建议是否与事实和法律分析一致。
- **标注方式：** 每项标记为通过、不通过或不适用。
- **单 Task 得分：** 通过的适用项数量 ÷ 全部适用项数量。
- **判定方式：** LLM Judge 按 Rubric 逐项评分，再由业务人员抽检校准。
- **严重错误：** 建议与已确认事实明显冲突，或者在证据不足时给出确定性结论。

> 大模型对比Agent输出结果和原数据集的处置建议，进行评分

### 3.5 多案件识别准确度

- **评估目标：** 输入多个案件，要求 Agent 按 `caseId` 输出结构化事实，再与人工标注的人物、时间、地点、行为、关键数值、责任和案件后果逐项比较。
- **数据构造：** 常规评测每条包含 3～4 个案件，压力评测每条包含 10 个案件；覆盖不同案由、相同或相近案由，以及多案件输入但只提取指定案件三类场景。
- **统一 Rubric：** 一个事实的内容正确且位于正确 `caseId` 下才记为正确；遗漏记为未召回；内容错误或归属错误记为错误输出。前两类使用同一 Rubric，只是数据难度不同；指定案件类另外检查是否输出非目标案件事实。
- **精确率：** 正确提取且归属正确的元素数 ÷ Agent 输出元素总数。
- **召回率：** 正确提取且归属正确的元素数 ÷ 人工标注元素总数。
- **F1：** 精确率和召回率的调和平均值。
- **跨案件错误率：** 放错 `caseId` 的元素数 ÷ Agent 输出元素总数。
- **非目标事实泄漏率：** 指定案件任务中，来自非目标案件的元素数 ÷ Agent 输出元素总数。
- **单 Task 通过条件：** F1 不低于 80%，目标案件没有遗漏，跨案件错误数为 0；指定案件任务还要求非目标事实泄漏数为 0。
- **判定方式：** 代码解析 Agent JSON 后进行字段和值归一化并逐项匹配，不再由 LLM Judge 整体判断。

## 4 工具调用判断评测集

同时准备需要调用和不需要调用 RAG 的问题，由人工提前标注 `shouldCallRag`，再与 Agent 是否实际产生 `search_legal_kb` 的 `tool.started` 事件进行对比。

| 人工标注 | Agent 实际行为 | 结果 |
| --- | --- | --- |
| 应调用 | 已调用 | 正确调用 |
| 应调用 | 未调用 | 漏调 |
| 不应调用 | 已调用 | 误调 |
| 不应调用 | 未调用 | 正确不调用 |

评估指标包括：

- **工具调用准确率：** 正确调用和正确不调用的样例数 ÷ 总样例数；
- **工具调用精确率：** 正确调用数 ÷ Agent 实际调用工具的样例数；
- **工具调用召回率：** 正确调用数 ÷ 人工标注应调用工具的样例数；
- **误调率：** 不应调用但实际调用的样例数 ÷ 不应调用样例数；
- **漏调率：** 应调用但没有调用的样例数 ÷ 应调用样例数。

## 5 评测执行

每条 Task 在固定的模型、Prompt、RAG 和上下文配置下运行，并保存最终回答、工具调用事件和运行状态。

由于模型输出存在随机性，关键 Task 可以运行 3 次，记录：

- 平均通过率；
- 3 次全部通过的比例；
- 最差一次结果；
- 是否出现一票否决问题。

模型、Prompt、RAG 或代码发生变化后，重新运行相同评测集，与上一版本结果进行比较。编造事实、编造法条、虚假 `sourceId` 和越权调用工具等问题实行一票否决。
