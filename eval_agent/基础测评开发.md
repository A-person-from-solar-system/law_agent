# Agent 基础测评开发方案

## 1. 开发目标

先实现一套可以完整跑通的离线测评程序：读取固定数据集，调用真实 Agent，保存本轮回答和工具事件，计算指标并生成报告。

首版只评估：

1. 事实识别准确性；
2. 来源可追溯性；
3. 处置建议合理性；
4. 多案件识别准确度；
5. 工具调用判断能力。

法律依据准确性暂不实现，也不计入总分。

## 2. 最简评测流程

```text
读取数据集
  → 补全 source_task_id 引用的案件内容
  → 逐条调用真实 Agent
  → 收集最终回答、RAG 结果和 SSE 事件
  → 按指标评分
  → 生成 JSON 和 Markdown 报告
```

首版采用串行执行，每个 Task 只运行一次，暂不实现并发、任务队列和多次试验。

│  ├─ judge_client.py         # 调用评分模型

## 4. 模块职责

### 4.1 配置模块

只保存测评运行需要的配置：

- 中台或 Agent 的接口地址；
- 测评使用的模型和评分模型；评分模型默认复用 Agent Engine 的模型配置，也允许通过 `EVAL_JUDGE_*` 单独覆盖；
- 请求超时时间；
- 数据集、运行结果和报告目录；
- 本次运行的版本名称。

密钥和服务凭证从环境变量读取，不写入数据集和报告。

### 4.2 数据加载模块

负责读取 JSONL 数据，并将引用型 Task 转成可以直接运行的完整输入。

- `tasks_eval_v1.jsonl`：直接读取案情、问题和参考答案；
- 多案件数据：根据每个 `source_task_id` 加载对应的 `case_facts` 和 `fact_points`；
- 工具调用数据：正样例加载原始案件和问题，负样例加载原始案件后使用当前 Task 中的问题覆盖原问题；
- 加载时检查 Task ID 是否重复、引用是否存在、必要字段是否缺失。

加载模块只负责准备数据，不调用 Agent，也不计算分数。

### 4.3 Agent 调用模块

负责调用当前系统已有的流式接口，并解析 SSE 事件。每条 Task 至少收集：

- Agent 最终回答；
- 是否出现 `search_legal_kb` 的 `tool.started`；
- RAG 工具返回的 `sourceId` 集合；
- `run.completed` 或 `run.failed`；
- 本轮错误码和总耗时。

调用模块不负责判断回答正确与否，只返回统一的运行结果。

### 4.4 运行记录模块

每次测评创建一个独立运行目录，原始结果使用 JSONL 保存。

```text
runs/{run_id}/
├─ run_config.json
└─ results.jsonl
```

每条运行结果至少包含：

- `run_id`、`task_id` 和数据集名称；
- 实际输入；
- Agent 最终回答；
- 工具是否调用；
- RAG 返回的 `sourceId`；
- 回答引用的 `sourceId`；
- 运行状态、错误码和耗时。

基础数据集不写入 Agent 输出，保证标准答案和每次运行结果相互独立。

### 4.5 评分模块

每项指标使用独立评分器，后续修改某个指标时不影响其他指标。

#### 事实识别评分

评分模型对比案件事实、人工 `fact_points` 和 Agent 回答，输出正确、错误、遗漏和不适用项，并计算精确率、召回率和 F1。

#### 来源可追溯性评分

使用确定性规则提取回答中的 `sourceId`，与本轮 RAG 返回的 `sourceId` 集合比对，计算有效引用数占总引用数的比例。

#### 处置建议评分

评分模型对比案件事实、`disposal_points` 和 Agent 回答，按照责任、后果、主观状态、从宽从重情节和结论一致性逐项判断。

#### 多案件评分

多案件任务要求 Agent 按 `caseId` 输出结构化事实。程序将结果与 `case_fact_map` 逐元素匹配，计算精确率、召回率、F1 和跨案件错误率；只提取指定案件的任务另外计算非目标事实泄漏率。多案件评分不依赖 LLM Judge。

#### 工具调用评分

使用确定性规则比较 `should_call_rag` 与是否出现 `search_legal_kb` 的 `tool.started` 事件，统计准确率、精确率、召回率、误调率和漏调率。

### 4.6 报告模块

首版只生成两个文件：

```text
reports/{run_id}/
├─ scores.json
└─ summary.md
```

`scores.json` 保存每个 Task 的详细评分；`summary.md` 汇总各项指标、失败 Task 和运行错误。

## 5. 统一运行结果

Agent 调用模块向所有评分器提供同一种运行结果：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 当前 Task 标识 |
| `answer` | Agent 最终回答 |
| `tool_called` | 是否调用 `search_legal_kb` |
| `rag_source_ids` | 本轮 RAG 返回的来源集合 |
| `answer_source_ids` | 回答中引用的来源集合 |
| `status` | `completed` 或 `failed` |
| `error_code` | 失败时的错误码 |
| `duration_ms` | 本轮总耗时 |

这样评分器不需要了解 SSE 和服务调用细节，只处理标准化后的数据。

## 6. 异常处理

首版只做基础处理：

- 单个 Task 失败后记录错误并继续下一个 Task；
- 接口超时、连接失败和 `run.failed` 单独记录为运行错误；
- 运行错误不直接当作回答质量 0 分，报告中单独统计；
- JSONL 格式错误或引用不存在时，运行前直接停止并提示具体 Task。

暂不实现自动重试、备用模型切换和失败任务队列。

## 7. 开发顺序

### 第一阶段：跑通数据和 Agent

1. 实现配置和数据加载；
2. 实现 `source_task_id` 引用补全；
3. 调用真实 Agent 并保存原始运行结果；
4. 确认可以获得最终回答、工具事件和 RAG `sourceId`。

### 第二阶段：实现确定性评分

1. 来源可追溯性评分；
2. 工具调用判断评分；
3. 生成基础汇总报告。

### 第三阶段：接入评分模型

1. 事实识别评分；
2. 处置建议评分；
3. 对少量结果进行人工核对，校准事实别名和归一化规则。

## 8. 首版验收标准

首版满足以下条件即可：

1. 四个数据集均能正常读取；
2. 引用型 Task 能正确还原完整案件输入；
3. 单个 Task 失败不会中断整次测评；
4. 能保存 Agent 回答、工具调用和 RAG 来源；
5. 五项启用指标均能产生 Task 级结果；
6. 能输出本次测评的 JSON 明细和 Markdown 汇总报告；
7. 相同数据集和配置可以重复运行并进行版本间比较。

## 9. 首版暂不实现

- 法律依据准确性评分；
- Web 管理页面；
- 数据库存储；
- 并发评测和任务队列；
- 自动重试和备用模型；
- 多次试验与 Pass@k；
- CI/CD 发布门禁；
- 在线实时评测。

这些能力等基础离线评测稳定后再逐步增加。
