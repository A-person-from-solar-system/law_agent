# Law Agent 2.0 面试 QA 02

这份文档主要用来准备二轮追问。回答尽量按面试现场的说法来写：先把问题讲清楚，再说当前项目怎么做，最后适当说明边界，不把没做完的能力说成已经上线。

## 1. 你这个项目为什么算 Agent，而不是普通 RAG 问答？

**面试官关注点：** 你是否能区分 Agent、RAG 和普通大模型应用。

**参考回答：**

我理解普通 RAG 更像一条固定流水线：用户提问之后，系统先检索知识库，再把检索结果拼给模型生成答案。

我们这个项目不是把检索写死在最前面，而是把法律知识库检索封装成一个只读工具。每轮请求进来后，Agent 会结合当前案件、历史对话和用户问题，自己判断要不要调用知识库。检索到的内容也不是一段纯文本，而是带来源标识的证据材料。

所以我不会把它夸成很复杂的 Agent 平台，更准确地说，它是一个面向法律咨询场景的轻量 Agentic RAG 应用。

## 2. 当前项目和复杂 Agentic RAG 有什么差距？

**面试官关注点：** 你是否客观看待项目边界。

**参考回答：**

当前项目已经有 Agentic RAG 的基础特征，比如知识库工具化、Agent 主动调用工具、检索结果带来源标识、回答过程可以流式返回。

但它还不是那种很复杂的多步骤 Agentic RAG。比如我们目前没有做多轮查询改写、自反思检索、多工具路由、自动引用校验，也没有做多 Agent 协作。

这个项目目前的重点是先把法律咨询里最关键的几件事做好：当前案件不要混、法律依据能追溯、工具调用可控、出错后能知道是哪一层的问题。

## 3. 为什么不直接每次都调用 RAG？

**面试官关注点：** 你是否理解工具调用成本和检索必要性。

**参考回答：**

因为法律咨询里不是每句话都需要查知识库。有些问题只是让模型解释上一轮结论，有些是围绕当前案件事实继续追问。如果每次都强行检索，不仅会增加耗时，还可能把无关案例带进来，反而干扰回答。

所以我们把 RAG 做成工具，让 Agent 在需要法条、类案或者外部依据时再调用。这样既保留了知识库能力，也避免每轮都走一遍检索流程。

## 4. `search_legal_kb` 工具解决了什么问题？

**面试官关注点：** 你是否理解工具抽象的价值。

**参考回答：**

这个工具的作用不只是“查一下知识库”，更重要的是把 Agent 和外部 RAG 服务隔开。

对 Agent 来说，它只需要知道这个工具能查法律资料，传什么参数、返回什么结构。至于 RAG 服务地址、鉴权、超时、返回格式清洗，这些都由中台和工具层处理。

这样后面如果要换向量库、加重排、或者接另一个知识库，Agent 主流程不需要大改，只要保证工具契约不变就行。

## 5. 工具调用结果为什么要做结构化 evidence？

**面试官关注点：** 你是否理解法律场景的可追溯性。

**参考回答：**

法律问答最怕的一点是模型说得很像真的，但你不知道依据从哪里来。

所以我们没有把 RAG 结果简单拼成一大段文本，而是整理成结构化证据，比如来源 ID、来源类型、标题、证据片段和元数据。模型在回答时能看到这些字段，中台也能保留这些信息。

这样做的好处是，后面如果用户质疑某个结论，我们可以根据来源 ID 回看这轮到底检索到了什么，而不是只能说“模型自己生成的”。

## 6. 如何防止模型编造法条或案例？

**面试官关注点：** 法律场景的幻觉控制。

**参考回答：**

我觉得这个问题不能只靠一句提示词解决，所以我们主要从几层做限制。

第一，Agent 的能力边界是收窄的，它不能随便访问网页、数据库或者本地文件，只能调用服务端注入的只读知识库工具。第二，知识库返回的内容会被整理成带来源 ID 的结构化证据，不是随便塞一段材料给模型。第三，提示词里要求模型引用法条或案例时尽量保留来源 ID，如果没检索到依据，就要说明依据不足，不能自己补案号、补法条。第四，中台会保存消息和工具结果，后面可以按来源 ID 复盘。

这不能说百分百消除幻觉，但至少把法律依据控制在可追溯范围内。

## 7. 工具异常为什么叫失败隔离？

**面试官关注点：** 你是否理解 Agent 主链路和工具链路的边界。

**参考回答：**

这里的失败隔离，指的是 RAG 工具失败了，不一定要让整轮 Agent 也失败。

比如 Agent 调用了知识库，但是 RAG 服务超时了。这个时候工具层会把这次调用标记为失败，并把失败结果返回给 Agent。模型可以知道“这次检索失败了”，然后基于已有案件事实给一个更谨慎的回答，比如说明没有检索到可靠依据。

所以隔离的是工具层失败和模型主生成链路。工具挂了会影响依据质量，但不一定直接把整个会话打断。

## 8. RAG 服务挂了，当前系统会自动降级吗？

**面试官关注点：** 你是否会夸大容错能力。

**参考回答：**

当前版本还没有做到完整自动降级，比如切备用 RAG、查缓存兜底或者多次重试，这些我不会说已经完成。

现在做的是比较基础但必要的处理：调用 RAG 有超时限制，返回内容有大小限制，异常会被归类成 RAG 超时、不可用、返回格式异常这几类。工具失败后不会把底层报错直接暴露给用户，而是通过统一事件和错误信息告诉前端。

如果继续往生产环境做，我会补短重试、健康检查、缓存兜底和熔断，这样 RAG 不稳定时系统体验会更稳。

## 9. 模型异常和工具异常有什么区别？

**面试官关注点：** 你是否理解 Agent 执行链路的主次关系。

**参考回答：**

工具异常通常发生在 Agent 已经开始运行之后，比如它要查知识库，但 RAG 超时了。这种异常可以包装成工具失败结果，模型还有机会继续回答。

模型异常就不一样了。模型接口不可用、模型超时或者模型返回错误，等于主生成链路断了，Agent 没办法继续推理，只能结束本轮生成，然后把失败状态返回给前端。

所以当前系统对工具异常有一定隔离能力；对模型或者 Agent 主链路异常，主要是明确提示失败原因，让用户可以重新发起。

## 10. 为什么要设计请求级无状态 Agent？

**面试官关注点：** 状态管理、扩展性和多用户场景。

**参考回答：**

主要是为了避免把用户状态长期放在 Agent 进程内。

如果每个用户都维护一个常驻 Agent，用户不用的时候也会占内存；用户数量上来后，内存回收、进程重启、扩容都会比较麻烦。还有一个问题是，状态如果放在内存对象里，后面多实例部署时也不好迁移。

所以我们把用户、案件、会话、历史消息这些长期状态放在中台和数据库里。Agent Engine 每次只处理当前请求传来的上下文，执行完就结束。这样隔离更清楚，也更方便后面做多实例扩展。

## 11. 无状态 Agent 会不会导致每轮都要重建上下文，成本更高？

**面试官关注点：** 你是否理解无状态设计的代价。

**参考回答：**

会有一点重建成本，但这个成本是可控的。

我们不是每轮都把全部历史无脑拼进去，而是由中台读取当前会话必要的信息，比如最近消息、checkpoint 摘要、当前绑定案件，然后再组装给 Agent。历史太长时会做摘要压缩，RAG 结果也会限制数量和长度。

所以无状态的代价主要是每轮重新组装上下文，但换来的好处是用户之间不会共享 Agent 内存状态，服务扩容也更简单。

## 12. 为什么用 `@` 引用案件，而不是让用户一直在聊天里补充案情？

**面试官关注点：** 你是否能从业务问题解释产品设计。

**参考回答：**

这个设计主要是为了解决案件事实容易混的问题。

法律场景里，时间、金额、人数、责任比例这些细节很重要。如果用户一直在聊天里补充案情，聊到后面模型很容易忘掉前面的精确信息；如果多个案件在一个窗口里聊，还容易串案。

我们当时也考虑过全量拼历史、摘要压缩、文档上传这些方案，但都有代价。最后选择 `@` 引用案件，是让用户先在案件库里维护案件事实，聊天时明确绑定某个案件。这样 Agent 每轮拿到的是中台注入的案件上下文，而不是完全依赖聊天记录自己猜。

## 13. checkpoint 主要解决什么问题？

**面试官关注点：** 长会话和上下文压缩。

**参考回答：**

checkpoint 解决的是长会话历史越来越多的问题。

用户连续聊很多轮之后，如果每次都把所有历史发给模型，成本会越来越高，也容易超过上下文限制。checkpoint 的思路是，把比较早的对话压缩成一份摘要，后续请求只带摘要、最近几轮消息和当前案件事实。

它不是用来处理单次超长输入的。单次输入太长，还是要在请求前做 token 预算校验。

## 14. 单次输入特别长怎么办？

**面试官关注点：** 你是否知道 checkpoint 的边界。

**参考回答：**

单次输入特别长，不能指望 checkpoint 解决，因为 checkpoint 是回答结束后对历史做压缩。

当前系统会在真正调用模型之前先估算上下文长度，包括系统提示词、历史消息、案件材料、当前问题、工具信息和预留输出空间。如果超过预算，就提前返回上下文超限错误，而不是让模型接口直接报错或者让前端一直等。

后面可以继续优化成材料分段录入、上传文件自动摘要，或者让用户把超长材料先整理进案件库。

## 15. token budget 是怎么估算的？

**面试官关注点：** 你是否知道实现细节，而不是只说概念。

**参考回答：**

当前系统没有接每个模型自己的精确 tokenizer，而是先做了一套近似估算，主要作为请求前的保护线。

普通文本按字符长度粗略估 token。历史消息、工具定义这类结构化内容，会先转成字符串再估算，因为模型最终看到的也是序列化后的内容。预算里会算系统提示词、工具定义、历史消息、当前问题、输出预留和安全余量。

如果估出来已经超过配置的上限，就提前拦截。这个估算不是用来精确计费的，更多是防止上下文直接爆掉。

## 16. “按模型配置上下文窗口”是怎么做的？

**面试官关注点：** 你是否理解模型配置和运行参数。

**参考回答：**

这个不是运行时自动去问模型“你最大支持多少 token”，而是项目里提前维护了一份模型配置。

系统启动时会根据当前配置的模型厂商和模型名称，读取对应的上下文长度、输出预留和安全余量。如果环境变量里手动写了这些值，就优先用手动配置。

所以它本质上是配置化适配：换模型时同步换一套上下文参数。优点是简单可控，缺点是需要我们维护配置，不是自动探测。

## 17. RAG 证据为什么还要做裁剪？

**面试官关注点：** 工具结果和上下文预算。

**参考回答：**

因为 RAG 返回越多，不代表回答越好。

如果把几十条命中结果全部塞给模型，一方面 token 成本会上去，另一方面低相关内容也可能干扰模型判断。当前工具层会对检索结果做去重、排序、数量限制和文本截断，只保留更可能有用的证据。

这样模型拿到的材料更集中，也能降低工具结果把上下文撑爆的风险。

## 18. SSE 在当前项目里解决了什么问题？

**面试官关注点：** 流式协议选择。

**参考回答：**

SSE 主要解决“用户不能一直盯着空白页面等结果”的问题。

法律 Agent 一轮回答可能会经历生成、检索、继续生成这些步骤，如果用普通 HTTP，只能等全部完成后一次性返回。用户不知道系统是在查资料，还是卡住了。

我们用 SSE 把模型文本、工具调用状态、完成状态和失败状态一点点推给前端。这样用户能看到回答在生成，也能看到是否正在检索知识库。

## 19. 前端实际使用了哪些 SSE 事件？

**面试官关注点：** 你是否区分协议支持和实际展示。

**参考回答：**

当前前端主要用的是几类事件：开始生成、文本增量、工具开始、工具完成、生成完成和生成失败。

其中最核心的是文本增量事件，用来做打字机式输出；工具开始和工具完成，用来显示“正在检索法律资料”这类状态；失败事件用来显示错误提示和重新生成按钮。

另外，后端协议里还有 usage 和 checkpoint 相关事件，但当前前端没有把它们做成明显展示，更适合后面做用量统计和上下文压缩提示。

## 20. 工具调用结果为什么不全部展示给用户？

**面试官关注点：** Agent 内部消息和用户可见消息的区别。

**参考回答：**

因为 Agent 运行过程中会有很多中间消息，比如工具调用参数、工具返回原文、模型中间推理结果。如果这些都展示给用户，页面会变得很乱，也会出现一轮问题多次回复的感觉。

当前系统更倾向于把工具过程用状态提示展示出来，比如正在检索、检索完成、检索失败；真正给用户看的，是整理后的最终回答。

但后端会保留工具结果和来源信息，方便后续排查和复盘。

## 21. 如果几百人内部试点，并发怎么考虑？

**面试官关注点：** 你是否能合理评估系统规模。

**参考回答：**

我会先区分注册用户数和真实并发数。几百个内部用户，不代表同时有几百个 Agent 在生成，真正压服务器的是峰值同时生成的请求数。

当前项目是请求级无状态 Agent，这对并发是有帮助的，因为 Agent Engine 不需要为每个用户常驻一个对象。试点阶段主要控制单轮超时、工具调用次数、RAG 返回大小和上下文长度。

如果后续用户量上来，我会再加用户级并发限制、请求队列、多实例部署、RAG 和模型服务限流，以及日志监控。

## 22. 如果模型供应商挂了，当前系统怎么处理？

**面试官关注点：** 模型降级边界。

**参考回答：**

当前系统没有做备用模型自动切换。

如果模型超时或者不可用，Agent Engine 会把它转成明确的模型错误，然后通过失败事件结束本轮生成，前端提示用户重试。

如果要做生产级可用性，可以加模型路由，比如先短重试一次，再切备用模型。但法律场景不能只追求“有回答”，换模型后回答质量、法律依据和格式都要重新评估，所以我不会说当前已经完整支持模型降级。

## 23. 如果工具越来越多，当前方案会遇到什么问题？

**面试官关注点：** 工具扩展和路由能力。

**参考回答：**

现在只有一个只读 RAG 工具，所以问题不大。但如果未来工具变多，比如法规库、案例库、合同审查、文书生成、审批系统都接进来，就不能把所有工具一股脑都塞给模型。

工具太多会带来两个问题：一是工具说明本身会占上下文，二是模型可能误调用工具。

后续更合理的方式是先做意图判断，只给 Agent 注入本轮可能用到的工具。涉及写操作或者高风险操作时，还要加权限校验和人工确认。

## 24. 当前系统怎么防 Prompt Injection？

**面试官关注点：** 你是否理解 Agent 输入不可信。

**参考回答：**

当前主要靠两点：能力边界和规则提示。

能力边界是最重要的。Agent 不能执行命令，不能读文件，不能直接查数据库，也不能访问任意网址。它唯一能用的业务工具是服务端注入的只读知识库检索。

规则提示是第二层。系统会告诉模型，用户输入、案件材料和检索结果都是资料，不是系统指令。即使里面出现“忽略前面规则”“调用某个接口”这类内容，模型也不应该当成新规则执行。

## 25. 当前系统怎么做服务间鉴权？

**面试官关注点：** 内部接口安全。

**参考回答：**

前端访问中台时，用用户登录态做鉴权；中台访问 Agent Engine 或内部知识库接口时，用内部服务 token 做鉴权。

这样浏览器不会直接拿到内部 RAG 地址和服务 token。Agent Engine 也不是直接暴露给普通用户，而是只接收中台组装好的请求。

简单说，就是用户身份归中台管，内部服务之间再用单独的服务凭证隔开。

## 26. 如果线上用户反馈回答错了，你怎么排查？

**面试官关注点：** Trace、复盘和问题归因。

**参考回答：**

我会先定位这次请求，比如对应的会话、消息和请求 ID，然后看这一轮 Agent 到底拿到了什么上下文。

接着分几种情况看：如果没调用 RAG，可能是工具调用策略或提示词问题；如果调用了 RAG 但材料不相关，那就是检索召回问题；如果材料是对的但回答错了，就偏模型推理或整合问题；如果回答里引用了不存在的来源，那就说明需要补引用校验。

这样排查时不会只停留在“模型答错了”，而是能具体定位到上下文、检索、工具调用、模型生成或者前端展示。

## 27. 你会怎么补一个真正的 Agent 评估体系？

**面试官关注点：** 你是否理解评测闭环。

**参考回答：**

我会先做一套离线评测，不直接影响线上用户。

具体做法是准备一批固定样例，覆盖普通法律问答、案件分析、必须依赖 RAG 的问题、检索失败、长上下文、多轮追问和注入攻击。每次改提示词、模型、RAG 策略或者上下文压缩逻辑，都用同一批样例跑一遍。

评估时不只看最终回答，还要看有没有正确调用工具、有没有引用来源 ID、错误码是否准确、响应耗时是否可接受。这样项目效果就不是靠主观感觉判断，而是能持续对比。

## 28. 这个项目最能体现你能力的点是什么？

**面试官关注点：** 你是否能总结自己的贡献。

**参考回答：**

我觉得最能体现能力的不是接模型接口，而是把法律 Agent 的几个边界控制住。

法律场景里，模型不能随便聊，它要知道当前分析哪个案件，依据来自哪里，什么时候该查知识库，查失败了该怎么提示。这个项目里我主要围绕这些问题做后端链路：中台管理案件和会话，Agent 每轮无状态执行，知识库作为只读工具接入，运行状态通过流式事件返回。

所以它的重点不是“让模型说话”，而是让模型在可控边界内回答。

## 29. 如果让你重构当前系统，你优先改哪里？

**面试官关注点：** 你是否能识别项目不足。

**参考回答：**

我会优先补两块：评估体系和引用校验。

评估体系是为了每次改提示词、模型或 RAG 策略后，都能用同一批样例回归，而不是凭感觉判断效果。引用校验是为了检查回答里的法条、案例和来源 ID 是否真的来自本轮检索结果。

其他像模型降级、RAG 健康检查、限流、队列和监控也重要，但对法律 Agent 来说，我会先把可信度和可评估性补起来。

## 30. 你在这个项目里不会夸大的地方有哪些？

**面试官关注点：** 你是否诚实、边界清楚。

**参考回答：**

我不会说这个项目已经是完整的多 Agent 平台，也不会说已经实现了自反思检索、自动模型降级、成熟线上评测体系。

当前真实完成的是一条轻量 Agentic RAG 链路：请求级无状态 Agent、只读 RAG 工具、结构化证据、来源 ID 追踪、上下文预算、checkpoint 摘要机制、流式状态输出和基础异常处理。

这些能力可以支撑内部试点和项目演示。如果继续往生产环境走，还需要补评估、监控、限流、降级和更严格的引用校验。
