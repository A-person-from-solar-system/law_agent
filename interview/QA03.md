# Law Agent 2.0 面试 QA 03

这份文档基于当前简历继续向下追问，重点补充前两份 QA 没有展开的内容：个人贡献、案件库方案、并发一致性、流式中断、摘要可靠性、接口契约和问题追踪。回答按面试现场的口语表达来写，并区分当前已经实现的能力和后续优化方向。

## 1. 你说自己是核心成员，具体负责了什么？

**面试官关注点：** 你能不能讲清个人贡献，而不是把团队成果全部算到自己身上。

**参考回答：**

我主要参与的是 Python 中台和 Agent Engine 之间的核心链路，不是一个人完成整个项目。

具体来说，我重点参与了请求级无状态 Agent、案件上下文组装、上下文预算、长会话摘要、RAG 工具接入以及 SSE 事件和异常透传这些模块。登录、员工管理、案件库等业务接口也参与了开发和联调，但我会把它们归为团队共同产出，不会说成全部由我独立完成。

## 2. 你是怎么从用户问题推导出案件库方案的？

**面试官关注点：** 你是否真正参与过需求分析和方案设计。

**参考回答：**

用户最初反馈的不是“缺少案件库”，而是对话变长以后，模型容易忘记金额、时间、人数等精确信息；在同一个窗口讨论多个案件时，还可能把不同案件的事实混在一起。

我们分析后认为，问题在于案件事实长期散落在聊天记录中，模型每轮都要从历史对话里重新判断当前案件。最后我们把案件事实独立出来，让用户在案件库中维护材料，聊天时通过 `@` 明确选择案件，再由中台把对应内容注入本轮 Agent。这样当前分析对象由用户明确指定，不再完全依赖模型从聊天记录中猜测。

## 3. 用户案件库和 RAG 中的历史案例库有什么区别？

**面试官关注点：** 你是否分得清业务数据和检索知识库。

**参考回答：**

这两个库解决的问题不同。用户案件库保存的是当前用户正在处理的案件事实，例如当事人、时间、金额和事情经过，它决定“这轮在分析什么”。

RAG 中保存的是法条、历史案例或者其他法律资料，它解决“回答依据从哪里来”。前者作为案件上下文直接注入 Agent，后者只有在 Agent 调用检索工具时才会返回。简单说，一个是待分析对象，一个是参考依据。

## 4. 为什么案件事实还要由用户维护，不能全部让模型自动提取？

**面试官关注点：** 你是否理解法律数据中准确性和自动化之间的取舍。

**参考回答：**

模型可以辅助提取，但不适合直接把提取结果当成最终事实。法律案件中的金额、日期和责任比例很敏感，一次提取错误就可能影响后面的判断。

当前方案让用户维护案件正文和结构化事实，用户对内容有最终确认权。后续可以增加模型预填和差异提示，但仍然应该让用户确认后再保存，而不是让模型静默修改案件事实。

## 5. 用户在同一个会话里快速发送两次问题，会不会产生两轮回答互相覆盖？

**面试官关注点：** 你是否考虑过同一会话内的并发一致性。

**参考回答：**

当前系统会限制同一个会话同时只能运行一轮生成。中台在创建新一轮消息时会锁定会话记录，并检查 `active_turn_id`。如果该会话已经有回答正在生成，就返回 `SESSION_BUSY`，不会再启动第二个 Agent Run。

本轮完成、失败或者客户端断开后，中台都会清除这个运行标记。这样避免两轮流式结果交叉写入，也能保证会话消息序号的顺序。

## 6. 用户关闭页面或者网络中断后，后台还会继续生成吗？

**面试官关注点：** 你是否处理了流式连接的生命周期。

**参考回答：**

中台在推送 SSE 时会检查客户端是否已经断开，断开后把这一轮标记为取消。Agent Engine 也监听流连接关闭事件，一旦下游连接关闭就调用 Agent 的中止方法，并释放计时器和事件订阅。

所以当前设计不会让已经失去接收方的请求一直无意义地占用生成资源。中台同时会把待完成消息改成取消状态，并释放当前会话的运行标记。

## 7. 一轮流式回答还没结束时，数据库里是什么状态？

**面试官关注点：** 你是否理解流式响应和持久化之间的一致性问题。

**参考回答：**

中台在调用 Agent 之前，会先保存用户消息，并创建一条状态为 `pending` 的回复记录。只有收到完整的结束事件后，才会把 Agent 返回的新消息写入数据库，并把这一轮改成完成状态。

如果中途发生异常或断开，就把这条待完成记录改成失败或取消，同时记录原因。这样数据库里不会把一个只生成了一半的回答误认为成功，也能看出这轮请求最终停在什么状态。

## 8. 为什么数据库要保存 Agent 原始消息，而不只是最终回答文本？

**面试官关注点：** 你是否考虑过上下文回放和工具调用复盘。

**参考回答：**

最终文本只适合给用户展示，但下一轮 Agent 还需要知道上一轮发生过哪些工具调用，以及工具结果和回答之间是什么关系。

因此中台除了保存可展示文本，还保存 Agent 原始消息结构，包括用户消息、工具结果和 assistant 消息。前端只读取用户需要看的内容，Agent 组装历史时则读取完整消息。这样既避免页面出现多次中间回复，也保留了后续回放和排查所需的信息。

## 9. Python 中台怎么确认收到的 SSE 事件属于当前请求？

**面试官关注点：** 跨服务流式响应是否有基本的数据校验。

**参考回答：**

每轮请求都会带一个 `requestId`。Agent Engine 发出的开始、文本、工具和结束事件也会带回同一个标识。

Python 中台解析事件时会检查事件里的 `requestId` 是否和当前请求一致。如果不一致，就按无效 Agent 流处理，而不是继续转发。这个检查主要防止连接复用、实现错误或者异常响应导致事件串到错误的请求中。

## 10. Python 和 Node.js 使用不同语言，怎么避免接口字段对不上？

**面试官关注点：** 你是否考虑过跨语言服务的契约维护。

**参考回答：**

两个服务之间不共享内存对象，所以关键是把 HTTP 和 SSE 数据结构固定下来。Python 侧用数据模型约束请求字段，Node.js 侧也会校验 Agent Run 请求；返回时只允许约定的事件类型，中台还会检查完成事件中的消息列表和请求标识。

当前主要靠两侧的数据模型和集成测试维护契约。后续如果团队规模更大，我会进一步抽成 OpenAPI 或 JSON Schema，由同一份定义生成两侧类型，减少人工同步成本。

## 11. 为什么 checkpoint 要在回答完成后异步生成？

**面试官关注点：** 你是否理解主链路延迟和后台任务之间的取舍。

**参考回答：**

摘要压缩还要额外调用一次模型，如果放在用户请求的主链路里，用户必须等摘要完成后才能收到本轮结束，响应时间会被直接拉长。

所以当前系统先完成回答并落库，再判断会话是否达到压缩阈值；需要压缩时，把任务放到后台执行。摘要失败不会影响已经完成的回答，下一轮最多继续使用原来的 checkpoint 和未压缩历史。

## 12. 如果同一个会话同时触发两个摘要任务，会不会互相覆盖？

**面试官关注点：** 你是否考虑过异步任务的并发写入。

**参考回答：**

摘要任务读取 checkpoint 时会记住当前版本号，写回时要求数据库中的版本仍然和读取时一致，并且新的覆盖位置必须比原来的位置靠后。

如果另一个任务已经先更新了 checkpoint，后写入的旧任务就不会覆盖新结果。这里相当于使用版本号做乐观并发控制，避免较旧的摘要把较新的摘要覆盖掉。

## 13. 如何降低摘要压缩丢失关键案件事实的风险？

**面试官关注点：** 摘要本身也是模型输出，你有没有考虑其可靠性。

**参考回答：**

当前摘要不是让模型自由写一段话，而是要求它按固定字段输出，例如已确认事实、未确认主张、时间线、金额、争议焦点、引用依据和待确认问题。生成温度设为零，返回后还会校验字段和 JSON 格式。

另外，系统会保留最近若干轮原始消息，数据库中的完整历史也不会被删除。这样摘要主要负责压缩较早内容；如果摘要生成失败，就不更新 checkpoint，不会用一份格式错误的结果替换原状态。

## 14. 有了 `sourceId`，是否就能证明模型引用的内容一定正确？

**面试官关注点：** 你是否会把“可追溯”夸大成“可信”。

**参考回答：**

不能。`sourceId` 只能说明这条材料来自哪次检索命中，方便回查原始来源，并不能自动证明材料真实、仍然有效，也不能证明模型对材料的解释正确。

当前系统做到的是来源可追溯。要进一步提高可信度，还需要校验回答中的来源 ID 是否真的存在于本轮证据中，并结合文书类型、生效时间和人工审核判断来源能不能作为法律依据。

## 15. RAG 返回的相关性分数可以直接当成可信度吗？

**面试官关注点：** 你是否理解检索相关性和事实正确性的区别。

**参考回答：**

不能。相关性分数只反映检索结果和查询在排序上的接近程度，不代表这条材料一定真实、有效或者适用于当前案件。

当前工具层可以利用分数对候选结果排序，但系统提示词仍然要求模型区分法规、案例和一般知识材料。法律结论不能只看分数高低，还要结合来源类型、时间和案件条件做判断。

## 16. 简历里写“20+ 个接口联调”，这里的联调具体指什么？

**面试官关注点：** 这个数字是不是简单数路由，以及你在其中做了什么。

**参考回答：**

这里的联调不是只确认接口能返回 200，而是检查前端、中台、Agent Engine 和 RAG 之间的字段、鉴权、状态码和异常是否一致。

我重点参与的是聊天主链路和 Agent 相关接口，例如中台组装请求、Agent Engine 接收并流式返回、RAG 工具调用以及错误透传。登录、员工、案件和会话接口属于团队共同完成。我在面试中会按模块说明自己负责和参与的边界，不会只用“20+”代替具体工作。

## 17. 简历写“支持 8 类流式事件展示”准确吗？

**面试官关注点：** 你是否清楚协议能力和前端实际使用之间的差别。

**参考回答：**

严格来说，这句话需要收紧。当前链路定义了 8 类事件，覆盖运行开始、文本增量、工具调用、用量、完成、失败和摘要待处理等状态；但前端实际重点处理的是文本、工具状态、完成和失败，`usage` 与 `checkpoint.pending` 还没有做成明显的页面展示。

因此简历更准确的写法是：“设计并联调 Agent Run 流式事件协议，覆盖模型生成、工具调用、运行结果和异常状态，并支持前端展示文本增量与检索进度。”这样不会把协议已支持误写成 8 类事件都已经可视化。

## 18. 如果要给系统增加日志能力，你准备记录什么？

**面试官关注点：** 你是否能把日志用于定位问题，而不是简单打印文本。

**参考回答：**

我会围绕一次 Agent Run 记录结构化日志，并用同一个 `requestId` 串起中台、Agent Engine 和 RAG 调用。主要记录请求开始和结束、会话标识、模型信息、上下文估算、工具名称和耗时、证据数量、token 用量、最终状态以及错误码。

法律案件可能包含敏感信息，所以日志不应该直接保存完整问题、案件正文和 RAG 原文。需要查看内容时，应通过受权限控制的数据库记录复盘；普通运行日志只保留标识、指标和经过脱敏的错误信息。

## 19. 现在项目里已经有完整的日志追踪系统了吗？

**面试官关注点：** 你是否区分已有基础能力和完整可观测平台。

**参考回答：**

现在已经有一些基础能力，例如请求标识、Agent 成功和失败日志，以及请求数、成功数、失败数、取消数、上下文拦截数和工具调用数等进程内指标。

但它还不能算完整的日志追踪系统，因为目前没有统一日志存储、跨服务检索、耗时链路展示和告警。下一步可以先统一结构化字段，再接入集中式日志和监控平台，让一次错误能够按 `requestId` 查完整条链路。

## 20. 健康检查返回正常，能否说明整个问答系统可用？

**面试官关注点：** 你是否理解存活检查和依赖可用性的区别。

**参考回答：**

不能。当前健康接口主要说明中台或 Agent Engine 进程还活着，Agent Engine 还会返回一些进程内运行指标，但它不能证明数据库、模型服务和外部 RAG 都正常。

如果用于生产环境，我会把检查分成两类：存活检查只判断进程是否需要重启；就绪检查再验证关键配置和依赖连接。模型和 RAG 还应通过独立探测和告警监控，不能把所有检查都塞进一个接口里。

## 21. 你怎么证明“降低了长会话成本”，而不是停留在设计描述？

**面试官关注点：** 简历中的效果是否有数据支持。

**参考回答：**

目前可以从机制上说明：达到阈值后，较早历史会被 checkpoint 摘要替代，后续只发送摘要和最近消息，因此输入长度不会一直跟着会话轮次线性增长。

但如果要把“降低多少成本”写成量化结果，还需要做对照测试：用同一批长会话分别运行全量历史和 checkpoint 方案，比较每轮输入 token、首字延迟和回答完整性。在没有这组数据之前，我会写“控制上下文膨胀风险”，不会编一个节省比例。

## 22. 这个项目目前最容易被追问的不足是什么？

**面试官关注点：** 你能否客观说明系统距离生产化还有多远。

**参考回答：**

我认为主要有三点。第一，来源 ID 目前解决了追溯问题，但还缺少自动引用一致性校验；第二，已有测试和基础指标，但还没有形成固定评测集和线上质量闭环；第三，外部 RAG 由其他团队维护，目前接口还没有统一的服务鉴权和完整降级能力。

这些不会否定当前系统的价值，但说明它更适合作为内部试点版本。继续生产化时，我会优先补引用校验、评测回归和跨服务可观测性。

## 23. 如果面试官认为这个项目只是把几个服务串起来，你怎么回应？

**面试官关注点：** 你能不能讲出集成工作中的技术含量。

**参考回答：**

服务串联本身不难，真正的工作在于确定数据和状态边界。比如案件事实由谁维护、哪些历史进入模型、什么时候压缩、工具失败是否终止整轮、流式中断后消息如何落库，以及检索来源怎么保留下来，这些都不是简单调一次接口能解决的。

我在项目中的工作重点，就是把这些边界落到上下文组装、会话状态、工具契约、SSE 事件和异常处理上，让系统不仅能跑通，还能处理长会话和失败场景。

## 24. 如果重新写这段简历，你最想补充什么数据？

**面试官关注点：** 你是否具备用数据说明工程价值的意识。

**参考回答：**

我最想补的不是接口数量，而是能体现方案效果的数据。例如案件绑定后多案件事实混淆率的变化、checkpoint 前后的平均输入 token 和延迟、RAG 工具调用成功率，以及一次错误按请求标识定位所需的时间。

这些指标比“写了多少接口”更能说明系统是否真正解决了问题。目前如果还没有完成正式测量，我会如实说明，并把它作为下一阶段评测和日志建设的重点。
