# Law Agent 2.0 面试 QA 01

本文从面试官视角整理当前项目的高频追问与参考回答。回答口径偏项目答辩和技术面试，重点突出架构取舍、Agent 设计、RAG 接入、上下文管理、工程稳定性和安全边界。

## 1. 请你简单介绍一下这个项目

**面试官关注点：** 你能否用清晰的话讲明白项目目标、用户场景和技术边界。

**参考回答：**

这个项目是一个面向政企内部使用的法律智能咨询系统，主要解决普通大模型在法律场景中容易出现的案情混淆、依据不可追溯、会话状态不可控等问题。

系统由三部分组成：前端是 Next.js Web 工作台，负责登录、会话、案件库和流式展示；中台是 FastAPI，负责用户鉴权、案件和会话持久化、上下文组装以及 SSE 转发；Agent Engine 是 Node.js/TypeScript 服务，基于 `pi-agent-core` 按请求创建无状态 Agent，并通过只读知识库工具调用 RAG 服务。

我的设计重点不是做一个简单聊天框，而是把法律咨询拆成“用户与案件管理、上下文管理、Agent 推理、知识库检索、结果持久化”几层，让系统更容易调试、扩展和上线。

## 2. 为什么把 Python 中台和 Node.js Agent Engine 分成两个服务？

**面试官关注点：** 你是否理解服务拆分的职责边界。

**参考回答：**

我把它们拆开主要是为了让有状态业务和无状态推理解耦。

Python 中台更适合做业务系统能力，例如 JWT 鉴权、员工管理、案件归属校验、PostgreSQL 持久化、会话历史读取和 checkpoint 压缩。Node.js Agent Engine 则只负责单次请求内的 Agent 创建、工具调用、模型流式输出和错误转换。

这样做有几个好处：第一，Agent 服务无状态，便于水平扩展；第二，权限和数据隔离由 Python 中台统一控制，Agent 不直接接触用户身份和数据库权限；第三，未来更换 Agent 框架或模型 Provider 时，不需要重写业务中台。

## 3. 为什么 Agent 要设计成无状态，而不是给每个用户维护一个常驻 Agent？

**面试官关注点：** 你是否理解 Agent 状态管理和多用户隔离风险。

**参考回答：**

常驻 Agent 虽然看起来可以减少上下文重建成本，但在多用户系统里会带来明显风险，例如用户之间串话、进程重启后状态丢失、内存难以回收、水平扩展困难。

当前系统采用“请求级 Agent”设计。每次用户发起咨询时，Python 中台从数据库读取可信会话状态、案件事实和 checkpoint 摘要，组装成一次 Agent payload 发给 Node.js。Node.js 创建新的 Agent，执行完成后返回增量消息，Python 再把结果落库。Agent 本身不作为长期状态真源。

这样状态真源只有数据库，进程内 Agent 只是计算对象，系统可恢复性和可观测性更好。

## 4. 当前系统的完整调用链路是什么？

**面试官关注点：** 你是否能讲清一次请求从前端到模型再回到前端的过程。

**参考回答：**

一次聊天请求大致是这样的：

1. 用户在前端选择会话和案件，发送问题。
2. 前端通过 `/api/chat` 调用 FastAPI，并接收 SSE 流。
3. FastAPI 校验 JWT、确认会话和案件属于当前用户。
4. FastAPI 从 PostgreSQL 读取历史消息、checkpoint 和案件事实，组装 Agent payload。
5. FastAPI 调用 Agent Engine 的 `/internal/v1/agent/runs`。
6. Agent Engine 创建请求级 Agent，注入系统提示词、历史、案件上下文和 `search_legal_kb` 工具。
7. Agent 需要法律依据时调用工具，工具通过 Python 中台再调用外部 RAG 服务。
8. Agent 生成最终回答并以 SSE 返回。
9. FastAPI 持久化本轮完整 Agent 消息，前端只展示用户消息和最终 assistant 回复。

## 5. 你们的 RAG 是怎么接入 Agent 的？

**面试官关注点：** 你是否能区分 RAG、Tool Calling 和最终生成。

**参考回答：**

RAG 在系统里不是直接生成最终答案，而是作为 Agent 的只读工具存在。Agent Engine 暴露一个 `search_legal_kb` 工具，工具内部调用 Python 中台的 `/internal/knowledge/search`，Python 中台再调用外部 RAG 服务的 `/retrieve` 接口。

外部 RAG 返回的是结构化命中，例如 `hit_id`、文本片段、分数、来源类型和 metadata。Python 会把它规范化成统一的 evidence 结构，包括 `sourceId`、`sourceType`、`title`、`excerpt` 和 `sourceMetadata`。Agent 拿到这些证据后再综合案件事实生成回答。

这样的好处是 RAG 只负责检索证据，Agent 负责推理和表达，职责比较清楚，也方便后续替换向量库、BM25、rerank 或外部知识服务。

## 6. 为什么不让前端直接调用 RAG？

**面试官关注点：** 你是否理解安全和链路控制。

**参考回答：**

前端不应该直接调用 RAG。首先，RAG 可能涉及内部知识库地址、鉴权 token 和检索策略，暴露给浏览器会有安全风险。其次，用户的问题需要结合会话、案件、权限和历史上下文，前端没有资格决定该检索哪些内部材料。

在当前架构中，前端只负责交互，Python 中台负责权限和上下文，Agent 负责判断是否需要检索，RAG 只提供只读检索结果。这种链路更适合企业内部系统。

## 7. 你们如何避免 Agent 访问不该访问的数据？

**面试官关注点：** 多租户隔离和权限边界。

**参考回答：**

数据隔离主要放在 Python 中台完成。所有前端请求都携带 JWT，中台根据当前用户 ID 查询会话和案件，并校验 `user_id` 是否匹配。Agent Engine 不直接读取数据库，也不接收任意用户 ID 后自行查库。

知识库工具也是服务端注入的固定工具，Agent 不能传任意 URL，也没有文件、命令行、数据库写入等工具。它唯一能用的业务工具是只读法律知识库检索。

因此权限边界不是靠提示词约束，而是靠后端 API、数据库查询条件和工具白名单来保证。

## 8. 当前系统怎么做上下文管理？

**面试官关注点：** 你是否理解长会话、案件事实和 token budget。

**参考回答：**

上下文管理分为两层。Python 中台负责从数据库读取 checkpoint 之后的消息、当前绑定案件和结构化事实，并组装成 Agent payload。Agent Engine 负责估算系统提示词、工具 schema、历史消息、案件上下文、当前 prompt、预留输出和安全余量的 token 总量。

如果超过预算，Agent Engine 会返回 `CONTEXT_BUDGET_EXCEEDED`。同时系统支持 checkpoint 机制，当会话轮次或估算 token 达到阈值时，中台可以把较早消息压缩成结构化摘要，后续只发送摘要和最近消息。

另外，针对不同模型上下文窗口不同的问题，Agent Engine 支持按 `MODEL_PROVIDER + MODEL_ID` 选择上下文档案，例如 DeepSeek V4 Flash 可以使用更大的上下文配置。

## 9. 为什么需要 checkpoint，而不是直接把全部历史都传给模型？

**面试官关注点：** 成本、稳定性和长会话设计。

**参考回答：**

全部历史都传给模型在短会话里可以，但长期使用会有三个问题：成本高、延迟高、容易超过上下文窗口。

checkpoint 的作用是把较早的对话压缩成结构化摘要，保留案件事实、争议焦点、引用法条、工具检索结果、待确认问题等关键信息。这样后续请求只需要携带 checkpoint、最近若干轮消息和当前案件事实。

它不是物理删除历史消息，而是改变 Agent 上下文读取范围。前端仍然可以展示完整历史，Agent 则使用更紧凑的上下文。

## 10. 为什么使用 SSE，而不是普通 HTTP 或 WebSocket？

**面试官关注点：** 你是否理解流式生成的技术选择。

**参考回答：**

普通 HTTP 只能等模型完整生成后一次性返回，用户体验较差，也不利于展示工具调用过程。WebSocket 能做双向通信，但对当前场景来说复杂度偏高。

SSE 很适合模型流式输出，因为它是服务端到客户端的单向事件流。当前系统通过 SSE 返回 `run.started`、`text.delta`、`tool.started`、`tool.completed`、`usage`、`run.completed` 和 `run.failed`。前端可以实时展示文本增量、工具状态和错误恢复。

对这个法律咨询场景来说，SSE 在能力和复杂度之间比较平衡。

## 11. 多次工具调用时为什么前端只展示最终回答？

**面试官关注点：** 你是否能解释 Agent 内部消息和用户可见消息的区别。

**参考回答：**

Agent 在一次运行里可能会产生多条 assistant 消息，例如先说明准备检索、调用工具、再补充检索、最后总结。如果把所有 assistant 消息都展示给用户，会像是系统连续回答了多次，体验上很割裂。

所以现在的设计是：数据库保留完整 Agent transcript，包括中间 assistant、toolResult 和最终 assistant，保证后续上下文可回放；但前端历史只展示用户消息和本轮最终 assistant 回复。

这相当于把“Agent 内部工作过程”和“用户最终阅读结果”分开处理。

## 12. 如果 RAG 服务挂了，系统怎么处理？

**面试官关注点：** 降级和错误分类。

**参考回答：**

RAG 调用在 Python 中台和 Agent Tool 层都有超时与错误处理。Python 中台调用外部 RAG 时会限制超时时间和响应体大小，并把错误归类为 `RAG_TIMEOUT`、`RAG_UNAVAILABLE` 或 `RAG_INVALID_RESPONSE`。

Agent Tool 收到失败后不会把底层异常暴露给前端，而是返回结构化工具失败事件。前端可以展示工具失败或生成失败提示。这样可以区分是 RAG 问题、Agent 问题、模型超时还是上下文超限，而不是都显示成“服务不可用”。

## 13. 如何防止模型编造法条或案例？

**面试官关注点：** 法律场景的幻觉控制。

**参考回答：**

这个问题不能只靠提示词解决，需要多层约束。

第一，系统提示词要求区分检索证据、案件事实和模型一般知识。第二，知识库工具返回结构化 evidence，并带有 `sourceId` 和 metadata，方便回答中引用。第三，RAG 检索不到时，Agent 应该明确说明未检索到可靠依据，而不是伪造来源。第四，前端和日志保留 sourceId，方便复盘一次回答用了哪些检索材料。

后续还可以继续加强，例如做引用强制校验、法条白名单校验、回答后验检查和专家评测集。

## 14. 你们怎么评估这个 Agent？

**面试官关注点：** 你是否知道 Agent 不只是“看起来会回答”。

**参考回答：**

我会分三层评估。

第一是业务能力，评估法律准确性、事实区分、法条和类案引用、量刑或责任分析是否合理。

第二是通用 Agent 能力，评估指令遵循、任务分解、工具调用、结果整合、长上下文稳定性和自我纠错。

第三是工程能力，评估响应延迟、成功率、错误分类、并发隔离、token 成本、日志可观测性和失败降级。

具体做法上，可以准备 30 到 50 条评测样例，覆盖普通问答、案件事实分析、RAG 检索、检索失败、长上下文、多轮追问和陷阱题。每条从准确性、证据引用、事实区分、推理完整性、可操作性和风险提示几个维度打分。

## 15. 这个项目里最重要的工程难点是什么？

**面试官关注点：** 你是否能总结复杂系统中的关键挑战。

**参考回答：**

我认为最核心的难点不是单个模型调用，而是让前端、中台、Agent 和 RAG 在多轮对话中稳定协同。

具体包括：如何保证 Agent 无状态但仍能获得完整上下文；如何让工具调用结果既能被模型使用又不会污染前端展示；如何在上下文超限、RAG 超时、模型失败时给出准确错误；如何保证用户和案件隔离；以及如何让 sourceId、messageId、sessionId 这些信息能支持后续排查和复盘。

这个项目的价值也主要体现在这些工程化边界上。

## 16. 为什么不直接用现成的大模型网页产品？

**面试官关注点：** 项目的必要性和业务价值。

**参考回答：**

通用大模型网页产品适合个人问答，但企业法律场景需要更强的数据治理和流程控制。

当前项目支持员工号登录、管理员开通账号、案件库、会话持久化、案件绑定、RAG 只读检索、sourceId 追踪和内部服务鉴权。这些能力不是一个普通聊天网页能直接满足的。

另外，法律场景需要明确区分案件事实、检索依据和模型推理，不能只追求回答流畅。自建系统可以把这些边界固化到架构里。

## 17. 如果要支持多个 RAG 服务，你会怎么设计？

**面试官关注点：** 可扩展性和抽象能力。

**参考回答：**

我不会让 Agent 直接知道每个 RAG 服务的细节，而是在 Python 中台保留统一的 `KnowledgeService` 抽象。不同 RAG 服务可以作为 adapter 接入，例如法规库、案例库、企业合同库或内部制度库。

对 Agent 来说，仍然只看到稳定的 evidence 结构。中台根据 query、sourceType、案件类型或配置决定调用哪个后端。这样未来替换向量数据库、增加 rerank 或接入第三方知识 API，都不会破坏 Agent 的工具契约。

## 18. 如果模型上下文很大，比如 1M，还需要 checkpoint 吗？

**面试官关注点：** 你是否会盲目依赖大上下文。

**参考回答：**

仍然需要。1M 上下文能缓解溢出问题，但不能消除成本、延迟和噪声问题。法律分析里，如果把所有历史、案件材料和检索结果都塞进去，模型反而可能被低价值信息干扰。

所以大上下文模型下，checkpoint 的意义从“防止塞不下”扩展为“控制信息密度”。系统应该优先保留高价值事实、最近对话和关键证据，而不是简单追求塞满窗口。

## 19. 当前系统还有哪些可以继续优化的地方？

**面试官关注点：** 你是否能客观看待项目不足。

**参考回答：**

可以继续优化的方向包括：

1. 引用校验：要求回答中的法律依据必须能映射到实际 `sourceId`。
2. RAG 质量：增加 hybrid search、rerank 和按案由/地区/时间过滤。
3. 上下文策略：按模型上下文、案件长度和 RAG 结果动态分配预算。
4. 管理后台：继续完善用户审计、角色权限和使用统计。
5. 评测体系：建立固定评测集，持续跟踪法律准确性和工具调用质量。
6. 部署安全：增加限流、审计日志、服务间强 token、HTTPS 和更细粒度的权限。

我会优先做引用校验和评测体系，因为它们直接影响法律场景的可信度。

## 20. 面试官如果问“这个项目最能体现你能力的点是什么”，怎么回答？

**参考回答：**

我觉得最能体现能力的是我没有把它做成一个简单的聊天 Demo，而是按真实企业系统去拆分了边界。

前端只负责交互，中台负责状态、权限和持久化，Agent Engine 保持无状态，RAG 作为只读工具接入。这样既能展示大模型能力，也能处理多用户、多案件、长上下文、工具调用、错误分类和可追溯这些落地问题。

从工程角度看，这个项目体现的是“把 Agent 能力产品化”的思路，而不是只调用一次模型 API。
